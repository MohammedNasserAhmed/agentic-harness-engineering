# grill-me

استخدم مهارة `grill-me` على مشروع **ShihrBorad**.

راجع توجه المنتج الحالي (Product Direction) ومتطلباته بصورة نقدية قبل تطوير أي وظائف جديدة. ركّز على المستخدمين المستهدفين، وأدوار الموظف والمشرف والمدير، ومؤشرات الأداء المالي، ودورة حياة المعاملات المالية، ومسارات الموافقة والاعتماد (Approval Workflows)، وانتقالات الحالات، والصلاحيات (RBAC)، وقواعد العمليات المالية، وإدارة الفروع، وسجل التدقيق (Audit Log)، وتجربة المستخدم العربية RTL، ومعايير النجاح، وحدود نطاق المشروع.

اطرح الأسئلة الأكثر أهمية، سؤالًا واحدًا في كل مرة. ناقش الإجابات الغامضة، واكشف التناقضات والافتراضات غير الواضحة، ولا تفترض متطلبات دون تأكيدها. لا تعدّل ملفات المشروع خلال مرحلة طرح الأسئلة.

عندما تصبح القرارات واضحة، لخّص ما يلي:

- قرارات المنتج المؤكدة (Product Decisions).
- الافتراضات المتبقية (Assumptions).
- المخاطر والحالات الحدّية (Risks & Edge Cases).
- معايير القبول للمرحلة القادمة (Acceptance Criteria).
- أصغر مرحلة تنفيذية تحقق قيمة فعلية (Minimum Useful Milestone).

احفظ موجز المنتج النهائي المتفق عليه في ملف `PRODUCT-BRIEF.md`، ثم وضّح ما أصبح أكثر وضوحًا نتيجة استخدام هذه المهارة.

# imrove-codebase-architicture

استخدم مهارة Improve Codebase Architecture على مشروع ShihrBorad.

افحص بنية المستودع (Repository Structure)، وتدفق البيانات في الواجهة الأمامية (Frontend Data Flow)، وحدود ومسؤوليات مسارات Express API، والأنواع المشتركة (Shared Types)، وقواعد العمليات المالية (Business Rules)، وآلية إدارة المعاملات والموافقات والصلاحيات، والتغطية الاختبارية (Test Coverage).

حدد المشكلة المعمارية الواحدة التي سيكون لمعالجتها أكبر أثر إيجابي، استنادا إلى أدلة فعلية من الكود الحالي.

**قبل إجراء أي تعديل:**

- اشرح المشكلة مع الإشارة إلى الملفات والأجزاء البرمجية المعنية.
- وضّح تكلفة استمرار المشكلة وتأثيرها على التطوير والصيانة والتوسع مستقبلا.
- اقترح إعادة هيكلة محددة ومركّزة (Focused Refactoring).
- حدد السلوك والوظائف وقواعد العمليات المالية التي يجب أن تبقى دون تغيير.
- وضح آلية التحقق من سلامة التعديلات (Verification Plan).

بعد ذلك، نفذ إعادة الهيكلة المقترحة فقط، مع الحفاظ على سلوك النظام، والصلاحيات، والوظائف المالية، وتجربة المستخدم العربية RTL. تجنب التعديلات والتحسينات غير المرتبطة بالمشكلة المحددة.

شغّل أوامر التحقق التالية:

- `npm run build`
- `npm run test`
- `npm run lint`
- `npm run typecheck`

أخيرا، قدم ملخصا يقارن البنية المعمارية قبل التعديل وبعده (Before/After Architecture)موضحا التحسينات المحققة، والملفات المعدلة، ونتائج التحقق الفعلية، وأي مشكلات متبقية.

# frontend-design

استخدم مهارة [$frontend-design] للارتقاء بتصميم الواجهة الأمامية لمشروع **ShihrBorad**.



حافظ على جميع مسارات العمل الحالية (Product Flows)، والوظائف المالية، والصلاحيات، وسلوك الـ API دون تغيير. حدد توجها بصريا احترافيا يعكس هوية مؤسسة مالية حديثة، ثم حسن الجوانب التالية:

- التسلسل البصري للمعلومات (Visual Hierarchy) داخل لوحة التحكم المالية.
- تجربة التنقل عبر أجهزة الحاسوب والهواتف.
- مؤشرات الأداء، والرسوم البيانية، وجداول المعاملات، والفلاتر، والنماذج، وطلبات الموافقة، وسجل الأنشطة، والإعدادات.
- الخطوط العربية الحديثة، والمسافات، والألوان، والأسطح، والأيقونات، ومتغيرات التصميم (Design Tokens).
- التكامل البصري بين الوضع الفاتح والداكن (Light/Dark Mode).
- التصميم المتجاوب (Responsive Design)، ودعم RTL، وسهولة التفاعل باللمس، وإمكانية الوصول (Accessibility).
- حالات الواجهة (UI States): التحميل، والبيانات الفارغة، والأخطاء، والتحويم، والتركيز، والتحديد.



تجنب التصاميم النمطية لصفحات الهبوط (Generic Landing Pages)، والزخارف غير الضرورية، والمظهر التقليدي للواجهات المولدة بالذكاء الاصطناعي. أعد استخدام المكونات (Reusable Components) حيث يعزز ذلك الاتساق البصري، دون فرض تخطيط موحد على جميع الشاشات.



اجعل الواجهة عربية بالكامل، عصرية، وأنيقة، مع كثافة معلومات مدروسة تناسب طبيعة الأنظمة المالية المؤسسية.



بعد التنفيذ، شغل الواجهة وافحصها بصريًا، ثم نفّذ أوامر التحقق التالية:

- `npm run dev`
- `npm run build`
- `npm run test`
- `npm run lint`
- `npm run typecheck`

أخيرا، قدم ملخصا للتوجه التصميمي المعتمد (Design Direction)، والملفات المعدلة، وأبرز التحسينات البصرية والوظيفية قبل التعديل وبعده (Before/After)، ونتائج التحقق الفعلية.

# performance

استخدم مهارة [$performance] لتقييم وتحسين أداء مشروع **ShihrBorad**.



افحص وقس أداء النظام، مع التركيز على الجوانب التالية:

- مخرجات بناء نسخة الإنتاج (Production Build) وحجم وتركيبة الحزم (Bundle Composition).
- سرعة التحميل الأولي للصفحات (Initial Route Loading).
- أداء عرض مؤشرات الأداء المالي، والرسوم البيانية، وجداول المعاملات، والفلاتر، وطلبات الموافقة، وسجل الأنشطة.
- طلبات الشبكة غير الضرورية، والاستدعاءات المتكررة للـ API، والعمليات الحسابية المتكررة.
- الاعتماديات والموارد كبيرة الحجم (Dependencies & Assets)، بما فيها الخطوط العربية.
- فرص تحسين تحميل المسارات والمكونات والبيانات (Routes, Components & Data Loading).
- أداء الواجهة على الأجهزة محدودة الموارد والاتصالات ضعيفة السرعة.



رتب المشكلات المكتشفة وفق تأثيرها المحتمل على تجربة المستخدم، وقدم أدلة وقياسات فعلية تدعم كل نتيجة. تجنب التحسينات الطفيفة القائمة على التخمين (Speculative Micro-optimizations).



نفذ أولا التحسين الآمن الذي يحقق أكبر أثر ملموس على الأداء. قارن القياسات قبل التحسين وبعده (Before/After)، وتأكد من بقاء الوظائف المالية، وقواعد الأعمال، والصلاحيات، وسلوك الـ API، وتجربة المستخدم العربية RTL دون تغيير.



شغل أوامر التحقق التالية:

- `npm run build`
- `npm run test`
- `npm run lint`
- `npm run typecheck`

أخيرا، قدم تقريرا مختصرا يتضمن المشكلات المكتشفة، والتحسين المنفذ، والملفات المعدّلة، ونتائج قياسات الأداء قبل التعديل وبعده، ونتائج التحقق الفعلية، والتحسينات المستقبلية التي تستحق التنفيذ.

# Security Review

استخدم مهارة [$security-review]  لإجراء مراجعة أمنية شاملة لمشروع **ShihrBorad**.



راجع المسار الكامل لتدفق البيانات (Data Flow)، بدءا من مدخلات واجهة React، مرورا بمسارات Express API، وصولا إلى تخزين البيانات المحلية. ركز على الجوانب التالية:

- آلية تسجيل الدخول التجريبي وإدارة الجلسات (Session Management).
- حدود الصلاحيات بين الموظف والمشرف والمدير (RBAC).
- مسارات إنشاء المعاملات المالية وتعديلها والموافقة عليها.
- سلامة قواعد العمليات المالية ومنع تجاوز مسارات الاعتماد (Approval Bypass).
- التعديلات على إعدادات الحساب والمؤسسة.
- البحث والفلاتر ومعاملات المسارات ومحتوى الطلبات (Input Validation).
- حماية البيانات المالية وسجلات التدقيق (Audit Logs) من الوصول أو التعديل غير المصرّح به.
- استجابات الأخطاء والتسريب غير المقصود للبيانات (Data Exposure).
- المخاطر الأمنية القابلة للاستغلال فعليًا في الاعتماديات وإعدادات النظام.



أبلغ فقط عن المشكلات الأمنية عالية الثقة والمدعومة بأدلة فعلية (Evidence-based Findings). وضح لكل مشكلة:

- مصدر الثغرة ومسار تدفق البيانات.
- الملفات والأسطر البرمجية المتأثرة.
- شروط الاستغلال (Exploitation Conditions).
- مستوى الخطورة والأثر المحتمل (Severity & Impact).
- أصغر إصلاح آمن وفعّال (Minimum Safe Fix).



لا تختلق ثغرات أمنية، ولا تعرض قيم الأسرار أو بيانات الاعتماد، ولا تعتبر الأنماط البرمجية العامة ثغرات دون إثبات إمكانية استغلالها.



بعد المراجعة، نفذ الإصلاحات الأمنية المحددة والمدعومة بالأدلة، وأضف اختبارات الانحدار (Regression Tests) لمنع تكرارها، مع الحفاظ على الوظائف المالية المشروعة وتجربة المستخدم العربية RTL.



شغل أوامر التحقق التالية:

- `npm run build`
- `npm run test`
- `npm run lint`
- `npm run typecheck`

أخيرا، قدم تقريرا أمنيا مختصرا يتضمن الثغرات المؤكدة، والإصلاحات المنفذة، والملفات المعدلة، ونتائج الاختبارات، والمخاطر المتبقية. إذا لم تجد ثغرات قابلة للاستغلال، اذكر ذلك بوضوح ووثق نطاق المراجعة وحدودها دون الادعاء بأن النظام آمن بالكامل.
